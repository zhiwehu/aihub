# AI Hub 变更说明：后台与演示客户端分离、统一记录管理、Intel Linux 适配

日期：2026-11-04

本文可直接作为 Codex 的实施任务。先核查当前代码与仓库内 AGENTS.md，再按本文调整；文中代码路径来自前期源码核查，实施时以当前分支为准。本文是目标要求，不代表这些改动已完成。

## 1. 目标与边界

1. `aihub-web` 只承担后台管理配置，以及管理员对各客户端记录的查看和管理。
2. 网页聊天、语音对话和录音演示从后台移出，成为独立演示客户端。
3. ESP32、网页演示及未来客户端统一接入 `aihub-server`，记录能按来源追踪。
4. 支持 Intel Core Ultra 5-225H、Linux；LLM/ASR/TTS 使用本机已部署的 HTTP 模型服务。
5. 保留现有 Mac 路径，避免 Linux 适配破坏原有部署。

本轮不开发 Apple Watch 客户端，不重写设备协议，不扩展成大型多租户平台。先完成架构边界与单机部署闭环。

## 2. 仓库职责

| 仓库 | 变更后的职责 |
|---|---|
| aihub-common | 公共音频、时间戳、错误和无模型的说话人聚类原语 |
| aihub-server | 协议网关、会话、录音落盘、记录管理、权限、工具编排、任务提交 |
| aihub-models | 模型适配与媒体后处理；Linux 路径通过 HTTP 调用现有模型服务 |
| aihub-tools | MCP、任务链、日历和其他助手能力，仍由 server 调用 |
| aihub-web | 管理员使用的后台管理配置与记录管理界面 |
| aihub-firmware | ESP32 固件、刷机与配网模块 |

网页演示客户端独立放在工作区 `clients/web-demo/`，有自己的说明、入口和静态资源，不再放入 `aihub-web/public`。该目录随相关实现纳入版本管理，可由 server 仓库托管（例如 `aihub-server/clients/web-demo/`）；不用为了本轮改动强制新建第七个远程仓库。

独立客户端指源代码、页面入口、资源和 API 权限独立，不强制要求独立端口或额外前端框架。可由 server 在 `/demo/` 提供；后台现有根入口尽量保留，避免无必要的 URL 迁移。

## 3. 后台与演示客户端划分

### 3.1 后台保留

- 模型服务地址、模型名、音色、采样率、鉴权引用等配置。
- 服务状态、日志、健康检查；仅对受管服务提供启停操作。
- 设备列表、在线状态、连接信息、令牌管理、配网和固件升级。
- MCP/Skills/工作流配置，以及已有管理功能。
- 对话记录、录音记录、转写、纪要、后台处理任务的查看和管理。

后台不再出现“打开本机麦克风开始聊天/录音”的交互。设备列表和记录页面可以展示已由客户端发起的活动状态；不在本轮新增后台远程启动设备录音。

### 3.2 独立演示客户端

- 文字聊天、麦克风语音聊天、回复播放、取消和现有打断行为。
- 开始/暂停/继续/结束录音，按当前协议支持范围实施。
- 查看本客户端有权访问的转写、录音回放与会议纪要。
- 通过公开的客户端 API/协议工作，不依赖后台 DOM、管理模块或管理员令牌。
- 不包含模型配置、设备令牌管理、固件刷写等管理能力。

拆分现有 `app.js` 时按管理、聊天、录音、公共 API/音频模块分开，避免把原大文件复制成两份。共享部分只包含通用逻辑，不反向依赖管理页面。

## 4. ESP32 等客户端的记录在哪里查看

后台提供两条路径，查询同一份服务端数据：

| 入口 | 内容 |
|---|---|
| 设备管理 → 某个设备 → 对话/录音 | 该设备的历史对话、录音、转写、回放、纪要与处理状态 |
| 数据记录 → 对话/录音 | 全部客户端记录，按来源、设备、时间、状态筛选 |

网页演示客户端也作为一个来源显示。未来接入新客户端时复用这套记录模型，无须另建一套记录后台。

服务端为记录保存稳定的来源关联，至少能够表达：客户端类型、客户端实例、可选设备 ID、会话 ID、可选录音 ID、创建时间。字段名沿用现有 schema；不要只靠设备显示名或临时 WebSocket ID 关联。

身份与来源信息由服务端根据已认证连接确定，不能信任客户端随意提交的 device_id。设备归属与用户归属分开表达，不强行把所有设备都当作用户账号。

历史记录保持可读。缺少来源的旧记录显示“历史记录/来源未知”，不得猜测归属或丢弃。优先使用兼容性读取与必要的增量迁移。

## 5. 聊天与录音的数据语义

- 聊天会话记录输入文本、回复、工具调用和必要状态。
- 聊天时采集的音频不自动成为持久会议录音，不因这次改造扩大原始音频保存范围。
- 客户端明确发起录音后，创建独立录音任务，保存音频及关联转写。
- 录音任务要有稳定 ID；暂停/恢复/结束的合法状态转换由服务端校验。
- 纪要、降噪、重分轨是关联录音的后处理任务，后台与客户端不重复生成两份记录。
- 断线后的录音状态、文件完整性、取消和错误展示沿用并核查现有机制，避免页面断开导致记录失联。

不要在没有实际音频落盘、转写或设备确认时显示“录音成功”。ESP32 是否已支持全部录音控制须核查固件与服务端协议，缺失项列明并实现必要兼容，不用网页状态冒充设备能力。

## 6. 接口与权限

逻辑上分为管理 API、客户端 API、设备协议三类。可优先保留兼容路由，不要求为了命名统一一次性改掉全部路径。

| 类别 | 权限 |
|---|---|
| 管理 API | 配置、服务管理、设备管理、全局记录管理，需要管理员权限 |
| 客户端 API | 聊天、录音、本人/本客户端授权记录及纪要，只能访问授权范围 |
| 设备协议 | 保留 ESP32 现有设备令牌与协议，按认证设备关联会话和记录 |

不能把管理员令牌放进演示客户端脚本，也不能通过放宽管理 API 鉴权来支持客户端。检查 WebSocket、录音音频下载、导出及纪要端点的访问控制。

优先复用已有认证机制，补充最小客户端配对/凭证能力，不要求新增注册系统。后台可查看所有来源记录；普通客户端不得仅凭 record_id 读取其他客户端数据。

保持管理后台默认本机访问。若支持局域网浏览器演示，配置单独的客户端访问方式与鉴权；麦克风页面必须满足 HTTPS 或 localhost 安全上下文，不能只开放普通 LAN HTTP 后宣称可录音。

## 7. Intel Ultra 5-225H Linux 适配

### 7.1 模型服务

LLM/ASR/TTS 已由本机独立服务部署，AI Hub 不需要在业务进程里重新加载模型。

| 服务 | 起步模型示例 | 当前 server 契约 |
|---|---|---|
| LLM | Qwen3.5-4B，量化版本按服务决定 | POST /v1/chat/completions，SSE delta.content |
| ASR | Qwen3-ASR 0.6B | POST /v1/audio/transcriptions，multipart WAV，返回 text |
| TTS | Qwen3-TTS 0.6B | POST /v1/audio/speech，单声道 s16le 裸 PCM |

三路配置均使用 `provider=http`，URL 可指向 127.0.0.1。模型名必须是服务实际接受的 ID；不在 Linux 默认配置中继续使用 MLX 模型仓库名。TTS 音色、采样率、返回格式必须对齐，不把 WAV/MP3 当裸 PCM。

服务不满足契约时加薄适配层。将实际 endpoint、模型名、超时等放入配置，不写死某套推理框架。需要非思考模式时按具体模型服务的支持方式配置，不能把思考文本直接朗读。

### 7.2 必须检查并修改的代码

| 位置 | 需要处理 |
|---|---|
| server/src/aihub_server/config.py | 增加可明确选用的 Linux HTTP 配置，移除该配置下的 macOS say/MLX 默认依赖 |
| server/src/aihub_server/pipeline.py | 复用 HTTP 适配，核查流式输出、PCM、异常、取消和超时 |
| models/src/aihub_models/minutes/inference.py | 当前直接加载 mlx_lm；增加 HTTP 纪要引擎，复用已有 Qwen3.5 服务 |
| models/src/aihub_models/__main__.py 的 make_transcribe | 当前走内置模型引擎；增加 HTTP ASR，供会后重新识别使用 |
| server/scripts/start_workspace.sh 及 deploy/docker/ | Linux 网络地址探测、外部模型状态与进程管理适配 |
| tools/src/aihub_tools/music_player.py | 当前 afplay 依赖；提供 Linux 后端或明确禁用并展示原因 |

上表 repo 缩写分别指 aihub-server、aihub-models、aihub-tools。

模型服务切换后，会议纪要与会后重新识别也必须走 HTTP，不能只改实时聊天。保留纪要模板、分段处理、证据、版本与导出逻辑。

### 7.3 依赖、资源和启动

- Linux 不安装 MLX extra `aihub-models[local]`，不复制 Mac 的 .venv 或 Rex 二进制依赖。
- VAD 继续在 server 本地运行，显式提供可用 ONNX 模型；安装必要重采样/编解码依赖。
- ffmpeg 用于媒体后处理；说话人识别所需 torch/speechbrain 按需安装和验证。
- 首版可使用现有 planner=llm；Rex 如需保留，单独准备 Linux 运行环境。
- 提供 Linux 安装说明、配置示例与 systemd 服务示例，分别管理 server 和后处理服务。
- 外部模型服务由其自身部署机制管理，AI Hub 不擅自启停。后台显示“外部服务”及真实探测状态，不能因缺少受管 PID 就判为失败。
- 不再通过扫描固定端口并 kill 的方式停止模型服务；只停止本系统明确拥有的进程。
- 对话与纪要共用 LLM 服务时限制后台任务并发，避免长纪要占满资源；跨进程调度须显式实现或交给模型服务，不能依赖进程内锁。
- 不承诺 225H 上的实时性能；在目标机器记录实际首字/首音延迟、转写耗时和内存占用。

## 8. 实施顺序

1. 核查当前页面、API、设备录音能力、记录 schema 与 Mac/Linux 依赖，列出具体修改点。
2. 抽离网页聊天/录音演示，后台保留管理功能；客户端调用路径脱离管理权限。
3. 补齐统一来源关联、设备详情记录入口及全局记录筛选。
4. 打通 Linux 的三路 HTTP 模型服务与录音闭环。
5. 将纪要、会后重新识别接入 HTTP，补 Linux 启动与运维说明。
6. 回归 Mac 路径与 ESP32 现有协议，完成下列验收。

每步保持系统可运行，不进行无关框架迁移或全量重构。保留现有数据，变更配置与数据前提供备份和回滚说明。

## 9. 验收标准

- 后台不请求麦克风权限，不再包含聊天/录音发起界面；记录回放与管理正常。
- 独立演示入口能聊天、语音对话和录音，不加载后台业务模块、不持有管理员凭证。
- 网页与 ESP32 的对话/录音均能在后台正确按来源查看；设备详情与全局列表打开同一条记录。
- 历史数据可读，未知来源有明确标识。
- 客户端无法越权读取其他来源的记录，也不能修改模型或设备管理配置。
- Linux 的实时 ASR/LLM/TTS、纪要及会后重新识别均走指定本地 HTTP 服务；无需 MLX/say/afplay 即可完成核心链路。
- 停止 AI Hub 不会停止独立模型服务；服务不可用时错误清晰，恢复后可重新使用。
- 验证 PCM 格式、流式取消、录音状态与落盘、长录音后处理，以及现有 Mac/ESP32 兼容性。
- 增加覆盖权限、来源归属、HTTP 纪要/ASR 和录音状态的必要测试；真实麦克风、设备、Intel 性能若未实测，交付中明确列出，不能用 mock 通过替代实机验收。
